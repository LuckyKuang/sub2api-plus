## Why

“安全审计 > IP 访问控制 > 登录失败状态”当前把持久化封禁规则、白名单覆盖和运行时执行开关压缩成一个 `currently_blocked` 布尔值，并且页面只在少数操作后刷新。与此同时，任一成功认证都会删除来源 IP 的失败窗口。这会让已经达到阈值的来源显示成较小计数或“未封禁”，也不符合“只封禁来源 IP、绝不锁定账号”的产品语义。

认证前规则缓存当前在短 TTL 到期或主动失效后由请求线程回源 PostgreSQL。攻击并发可以把一次缓存刷新放大为多次全量规则查询；固定缓存一天又会放大漏失效造成的误封或漏封，并且不能正确表达不同规则的 `expires_at`。

## What Changes

- 将登录失败窗口定义为来源 IP 维度；账号、认证成功和认证方式均不得清除该窗口。
- 达到阈值且确认持久化 active 自动封禁规则后，本次请求返回 `403 / IP_BANNED`；风控依赖失败或提交结果无法确认时返回 `503 / IP_ACCESS_CONTROL_UNAVAILABLE`。
- 将失败状态 API 拆成“有效 block 规则”“运行时执行开关”“被 allow 覆盖”“最终有效封禁”，并返回阈值、规则信息和状态时间点。
- 将认证前判定改为启动预热后的进程内安全快照；请求热路径不因 TTL 到期或失效直接查询 PostgreSQL。
- 使用后台定期刷新、事件触发刷新和 singleflight 合并回源；本实例提交规则后直接更新本地不可变快照。
- 缓存中的自然过期由每条规则的 `expires_at` 决定。不存在统一固定一天的封禁 TTL；永久规则持续生效但仍由后台周期对账。
- 管理员“重置失败计数”只清除窗口计数，不解封；“解封并重置”同时释放 block 规则并清除计数；allow 规则只覆盖 block，不删除 block。
- 在登录失败状态行提供经过 step-up 验证的“手动封禁”动作；该动作创建 exact-IP `manual_block`、保留失败计数，并且只有在当前执行条件下确认实际封禁后才报告成功。
- 管理页面提供手动刷新、最后更新时间和页面可见时的低频自动刷新，并展示分层状态。

## Capabilities

### New Capabilities

- `ip-login-failure-enforcement`: 定义 IP-only 登录失败窗口、封禁结果、认证前快照和管理状态展示语义。

### Modified Capabilities

无。

## Impact

- **安全边界**：认证入口、全局 IP 中间件、风控不可用时的 fail-closed 行为。
- **后端**：IP 访问控制服务、PostgreSQL 仓储、失效订阅、认证与 Passkey handler。
- **管理 API**：登录失败状态响应移除含义混杂的 `currently_blocked`，新增分层状态字段和幂等的 exact-IP 手动封禁动作。
- **前端**：登录失败状态表、手动封禁确认与提交状态、刷新行为和中英文文案。
- **持久数据**：本阶段不新增表或迁移；失败计数与规则仍由 PostgreSQL 持久化。
- **兼容性**：这是安全状态 API 的有意语义替换，不保留旧字段兼容层。

## Non-goals

本变更不锁定账号，不实现按账号失败计数，不用 `403` 表示未确认的临时隔离，也不在本阶段把失败计数或命中聚合迁移到 Redis。Redis 计数、持久化 leader、quarantine、policy version/outbox/tombstone 和规则历史归档另行作为后续持久数据变更实施。

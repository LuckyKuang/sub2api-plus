# 渠道监控：V1 探测、V2 被动聚合与 V3 服务状态

渠道监控提供三种互斥模式。V3 以全站所有用户真实请求的终态结果展示有效渠道的全局可用性与事件，不发送探测请求，也不表示供应商官方平台的全球状态。

## 模式与开启

在「系统设置 → 功能开关 → 渠道监控」开启功能，通过并排模式按钮选择 **V3 服务状态**，保存后即可从个人区「服务状态」进入 `/monitor`。在「渠道监控」管理页的 V3 标签配置判断阈值。
系统设置的功能开关保留并提交所选模式，保存 V3 后重新加载仍显示 V3。
V3 配置中的「启用平台监控」为每个具体平台提供独立开关，默认全部开启。
关闭后停止该平台的事实聚合、状态判断和事件推进，并从服务状态的卡片、筛选、
模型详情、历史、事件、摘要和计数中移除。V2 的平台开关不会影响 V3。
保存模式后，前端会使旧公开设置请求失效并重新读取已保存配置，避免旧响应覆盖新模式。
进入 `/monitor` 时重新读取模式；已打开的状态页在重新获得焦点或恢复可见时也会同步。
V1、V2、V3 分别挂载主动探测、被动监控和服务状态页面，切换时卸载前一种页面。
V1/V2 保留原有用户可见性、分组权限、指标隐藏开关和监控行为；开启后登录用户可从个人区进入对应页面。

| 模式 | 数据来源 | 可见范围 |
| --- | --- | --- |
| V1 | 配置的主动探测 | 保留原有页面和行为 |
| V2 | 被动用量聚合 | 登录用户，沿用授权分组范围以及吞吐、用户排行隐藏设置 |
| V3 | 真实用户请求的终态 | 所有登录用户共享全站有效分组的状态、历史和事件 |

默认模式仍是 V1。升级不会自动修改已有模式。选择 V3 时，V1 探测和 V2 聚合停止；V3 使用独立配置及聚合表，不依赖 V2 的启用开关、分组选择或阈值。切换模式保留各模式的已存历史；V3 恢复启用后继续观测，停用期间不自动补齐历史。

## V2 被动聚合与历史回填

缺失、空值或无效模式均归一到 V1；已有 V2 设置保持不变。V2 需要管理员明确选择，启用 V2/V3 后 V1 主动探测停止。V1 执行入口无法读取设置时不发起探测。

V2 按配置的 `refresh_interval`（60 或 300 秒）运行，不为首次启用强制改成 5 秒。单个聚合者持有领导锁，每次事务预算约 55 秒；每轮先重算最近约 10 分钟，再最多处理一个历史分块。首次种子覆盖 2 小时，优先满足默认 90 分钟视图；后续回填从 1 小时分块开始，逐步覆盖 1 天、7 天、30 天及最长 90 天保留范围。

分块最小 15 分钟，最大值按历史深度分别为：1 天内 2 小时、7 天内 4 小时、更早 6 小时。成功且耗时少于 15 秒时按 1.5 倍缓慢扩大；失败或超时则减半，并采用最长 10 分钟的指数等待。页面先显示已覆盖的数据，历史未回填完不表示没有请求。

错误去重只对本轮候选请求 ID 关联额外 90 分钟的日志，避免扫描完整错误历史。模式切换不强制把已有 V2 设置改回 V1，也不改写已发布迁移。

## V3 请求口径

聚合从 `usage_logs` 与 `ops_error_logs` 读取最近 10 分钟的数据，每分钟重算并提交事实、故障状态、事件记录和水位。相同请求 ID 的终态用量记录优先于中间重试错误，避免成功的重试被计为故障；同类记录选择最新一条。没有请求 ID 的记录按各自日志 ID 处理。候选 ID 的关联查询限制在额外 90 分钟内。

- `completion_status=completed` 或旧格式 `completion_status=unknown` 且 `is_complete=true` 才算成功。成功与费用、Token 数量无关，免费请求同样计入。
- 明确不完整的终态请求计为失败；关联错误用于排除用户侧原因。已扣费不代表请求成功。
- 客户端断连的终态记录覆盖中间重试错误，然后排除在统计分母之外。
- 输入无效、上下文超限、不支持的模型、分组权限、内容策略、客户端取消、用户鉴权／额度／限流等错误被排除。供应商鉴权／余额／容量失败、渠道无可用账号、超时、传输异常、供应商 5xx 和内部服务错误计为渠道失败。
- Token 计数错误和 `request_type=4` 的策略阻断记录被排除。压缩等真实请求若记录明确完成终态，遵循同一口径。
- 平台采用分组的有效平台，错误日志的协议平台不能覆盖分组平台；复合分组展开到实际账号平台。没有有效分组或平台的日志不对用户展示。
- 单轮超过 50,000 条规范终态时整轮回滚，保留旧水位并记录固定错误码；不得静默截断后报告正常。

这是有界日志观测：缺失的终态记录无法推断；到达过晚、超出最近 10 分钟重算范围或关联范围的日志可能不被修正。记录日志失败、延迟或不足均不能作为运行正常的证据。V3 不改动网关、请求审计、计费或供应商身份逻辑。

## 当前状态与故障事件

当前状态使用最近 **5 分钟**的合格请求。聚合水位延迟超过 **3 分钟**或没有近期请求时，显示未知。样本少于最低数时显示样本不足。当前状态与所选 24 小时／7 天／30 天的历史成功率是不同时间范围。

| 配置字段 | 默认值 | 允许范围 |
| --- | --- | --- |
| `minimum_samples` | 5 | 1–10,000 |
| `warning_error_rate` | 0.05 | 大于 0 且小于 1 |
| `outage_error_rate` | 0.9 | 不小于异常阈值，且不大于 1 |
| `warning_ttft_ms` | 5,000 | 100–300,000 毫秒 |
| `abnormal_windows` | 2 | 1–10 次新请求观测 |
| `recovery_windows` | 3 | 1–10 次新请求观测 |

错误率达到中断阈值显示中断，达到异常阈值显示部分异常；其余请求的 P50 首 Token 延迟超过阈值则显示性能下降。某个分组／模型异常可以提升整个平台的异常状态，防止被高流量健康模型掩盖。平台中断需要所有已知模型范围都处于中断；其他情况为部分异常。未结束故障的模型缺少足够数据时，其他健康模型不能令该平台显示已确认正常。

事件按「平台 + 分组 + 模型」持久化，同一范围最多一个未结束事件。确认故障和恢复必须看到比上一轮更新的请求时间；同一批样本重复扫描不会累加确认次数。异常等级变化仍算连续异常，正常与异常之间的切换会重置连续计数。

事件阶段为 `detected`（监控到故障）、`ongoing`（异常持续）、`recovering`（恢复观察）、`awaiting_data`（等待新请求）、`resolved`（已恢复）。无流量或样本不足会中断恢复确认，并保留未结束事件。恢复观察中再次异常会撤销恢复证据。事件不声称已识别根因或正在人工修复。

旧失败样本移出滚动窗口或管理员调整阈值后，即使当前聚合指标看似正常，也不能直接显示恢复观察；仍需新请求触发事件的恢复阶段。多个模型同时恢复和变慢时，性能下降优先于恢复观察，显示不受模型遍历顺序影响。

## 历史和页面

V3 使用匿名分钟事实保留 **31 天**，不保存请求 ID、用户、账号、费用或原始错误。已恢复事件保留 31 天，页面展示最近 30 天最多 200 条已恢复事件，以及全部未结束事件，摘要中的未结束计数不受 200 条上限影响。每个事件最多保留 32 个阶段更新，保留首个检测更新。停用期间不执行清理；重新启用后执行保留策略。长期无请求且无未结束事件的模型状态也会清理。

单个平台关闭时保留已有历史及未结束事件，事件冻结且不会被标为已恢复。
重新开启从保存后的下一个完整分钟开始观测；起点由服务端持久化，重启不会丢失。
最近 10 分钟重算不会补入平台停用期间的请求，也不会删除停用前的分钟事实。
当前状态仅使用本次重新开启后的请求；历史成功率仍包含保留范围内以前的观测。
连续故障和恢复确认次数重新积累，原未结束事件进入等待新请求阶段。
复合分组按其有效平台应用开关，协议名称不能覆盖有效分组或实际账号平台。
所有平台关闭时页面显示「暂无启用的监控平台」，不宣称服务正常；工作进程跳过
用量和错误日志扫描及事件推进，但在 V3 功能仍开启时继续执行 31 天保留清理。

首次启用只观测最近 10 分钟，此后逐步积累历史，不在启动时全量回填 30 天。历史显示 48 个对齐到所选时间窗口的区间；灰色区间表示无法判断。

TTFT 仅使用成功请求中 `timing_version=1` 的 `first_token_ms`。不以图片或音频首次输出替代首 Token。P50 是合并直方图得到的近似上界，页面用 `≈` 标注。16 个桶的毫秒上界为：50、100、250、500、1,000、2,000、3,000、5,000、8,000、10,000、15,000、30,000、60,000、120,000、300,000、2,147,483,647；自定义延迟阈值也受此近似影响。

平台名称文字使用品牌色，卡片和图标沿用项目中性色调，支持浅色及深色主题。顶部摘要保留状态文案、未结束事件数、平台计数和「查看事件」跳转；平台标签下不重复放事件列表。事件只在独立标签展示，平台卡片可打开分组／模型详情。

平台筛选使用项目统一的原生下拉框，文字左侧与箭头右侧均保留 12px 间距，箭头大小为 16px；浅色、深色主题一致。

## API 与权限

V1/V2 的用户只读接口保留原有权限。V2 的 `GET /api/v1/channel-monitor-v2/{dimensions,snapshot,models,matrix,errors,users}` 要求登录、渠道监控开启且模式为 V2，不额外要求管理员身份。普通用户的数据仍按授权分组过滤，吞吐、排行、其他用户身份及错误样本的展示沿用原有规则；管理端配置和管理接口仍要求管理员权限。

| API | 权限与参数 |
| --- | --- |
| `GET /api/v1/channel-monitor-v3/snapshot` | 登录用户，功能开启且模式为 V3；`range=24h|7d|30d`（默认 24h），可选 `platform` |
| `GET /api/v1/admin/channel-monitor-v3/config` | 管理员，渠道监控功能开启 |
| `PUT /api/v1/admin/channel-monitor-v3/config` | 管理员，功能开启；完整配置及 `version` |

配置保存在数据库单例 JSON 中，不增加部署环境变量。更新使用版本比较，过期版本返回 409，需刷新后重试。管理员权限、现有管理审计和面板限流继续生效。
`disabled_platforms` 为关闭平台名称的数组，空数组表示全部开启；旧配置缺少该字段
时同样全部开启。名称必须来自具体平台目录，重复、未知或复合平台名称返回 400。
将所有具体平台加入数组表示全部关闭，不能通过省略字段表达全部关闭。
目前目录为 `anthropic`、`openai`、`gemini`、`antigravity`、`grok`、`kimi`、
`zhipu`、`deepseek`、`minimax`、`opencode_go` 和 `typesafe`；新增平台默认开启。
服务端内部 `observation_starts` 元数据不出现在配置 API，也不接受客户端覆盖。
保存与聚合通过配置行锁同步，保存成功时使用旧配置的聚合已结束。
快照在同一可重复读事务中读取配置和数据，包含 `monitoring_enabled` 布尔值，
表示至少一个具体平台开关开启；它不表示平台有流量或服务健康。
关闭平台及请求的 `platform` 筛选均在已恢复事件的 200 条限制之前生效。

快照统一读取全站所有未删除且状态为 `active` 的分组，不按查看者的用户 ID、订阅或分组访问权限过滤。普通用户、没有分组权限的用户、管理员个人页及用户协助视图共享相同的全站状态和事件。所有事实、模型详情、历史、事件、摘要及计数遵守同一全局范围；删除或停用的分组不可见。客户端 `group_id`、`user_id` 或 `admin=true` 不改变数据范围；`platform` 筛选同时作用于状态与事件。全局观测不授予分组的模型调用权限。读取使用只读可重复读事务，不混用不同提交批次的事实和状态。公开 DTO 仅含安全的状态、比例、近似延迟、分组／模型名称与事件阶段，不含请求规模、用户排名、账号、费用或错误内容。

工作进程仅在模式 V3 且功能开启时运行，使用事务级互斥锁保证单个聚合者。请求超时为 45 秒。服务关闭时取消进程并等待退出；失败记录结构化日志 `service_status_refresh_failed`，包含固定 stage/code，且不输出原始错误或内容。

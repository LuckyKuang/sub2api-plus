These tests drive Chromium through the real login and administration pages.
The application uses its production handlers, services, PostgreSQL, and Redis.
Only outside proxy/provider destinations are isolated local responders. Browser
route interception and Axios adapters are not used.

The acceptance scope is the gateway functionality already implemented in this
repository, as inventoried in
[`SEVEN_PROVIDER_TEST_MATRIX.md`](../../docs/SEVEN_PROVIDER_TEST_MATRIX.md).
It does not require adding a provider feature that the gateway explicitly does
not support. In particular, native inline media does not establish general
DeepSeek/MiniMax Files upload, ownership, expiry, or deletion support.

The browser suite defines exactly 14 management scenarios: each of OpenAI,
Grok, DeepSeek, Kimi, MiniMax, StepFun, and Zhipu, with API Key and OAuth account
records. Scenario definitions are not evidence of a passing run. The owning
matrix records the final container execution result; this README does not
establish a passing result.

A separate fifteenth scenario, `composite billing: real browser edits and stale
policy conflict`, covers group configuration only. It creates a disposable
Composite group through the real admin API, edits platform/model factors through
the browser, verifies persisted zero/model rates and version increments, and
checks that a concurrent real API writer causes HTTP 409 while preserving the
browser draft. It does not establish inference, payment, account availability or
seven-provider authorization coverage. The runner requires this scenario
separately from the unchanged 14-case provider management manifest; focused
execution uses `--grep 'composite'` for billing policy and API Key rate disclosure.

| Existing management requirement | Independent acceptance observation in every applicable case |
| --- | --- |

Account record creation uses the real administrator API as fixture setup.
These 14 tests **do not** prove account creation through each provider's UI,
provider OAuth authorization, or live subscription validity. The OAuth records
contain synthetic stored credentials; they are not generated by an OAuth
issuer. Gateway protocol adaptation, native streaming/tools, credential refresh,
quota, selection/failover, Redis affinity, billing, Live, and ZCode ticket
lifecycles retain their separate unit/network/PostgreSQL/Redis evidence in the
owning matrix. Do not count this management chain as a browser-to-provider
authorization/inference/billing flow or use it to close those separate entries.

The separate Vue/API lifecycle regressions use the actual redacted account DTO:
provider tokens are absent, presence flags remain under `credentials_status`,
and `oauth_credential_owner` identifies the credential, saved route and recovery
state. A changed owner must revoke the active authorization even if account ID,
proxy ID, `updated_at` and token-presence flags are unchanged. Usage observations
or proxy name/timestamp changes with the same owner must preserve pending grants
and native ready sessions. The account list must propagate a changed owner to
its consumers. Grok chooses refresh-token reauthorization from the redacted
`credentials_status.has_refresh_token` flag.

Those regressions cover OpenAI/Grok existing-account grant/apply completions,
OpenAI device start/poll/apply and polling disposal, plus independent native
menu/editor reauthorization and account reloads for DeepSeek, Kimi, MiniMax and
StepFun. The native entrypoints use the saved account ID and region; the backend
owns its saved proxy. Zhipu currently offers new-account linking, with no
in-place account relinking UI. DeepSeek and Zhipu have no published business-login
refresh operation and expose no **Refresh token** action. These supported and
unsupported actions are component/API acceptance scenarios, separate from the
14 Chromium proxy-management cases.

Existing-account OAuth apply requests include the original DTO's
`oauth_credential_owner` as `expected_owner`. Missing or malformed values must
prevent sending replacement credentials; a conflict must restart authorization
without retrying the old grant against a newly fetched owner. Once an apply POST
has been sent, the server decides it through its owner comparison and atomic
conditional commit. Closing or replacing the UI flow cannot revoke an already
issued write. Its late response still cannot close, notify, or release loading
for a replacement flow. PostgreSQL transaction/CAS tests establish persistence
behavior; the component tests establish UI isolation. See the
[supported business inventory](../../docs/SEVEN_PROVIDER_SUPPORTED_BUSINESS.md)
and [authentication contract](../../docs/AUTHENTICATION.md) for the owning rules.

The maintained orchestration entrypoint is
`python3 tools/run_seven_provider_browser.py` in a disposable repository
validation container running as root. The launcher must provide
`SUB2API_E2E_ISOLATED=1`, `SUB2API_TEST_POSTGRES_DSN` (PostgreSQL URL),
`SUB2API_TEST_REDIS_ADDR`, and explicit `SUB2API_TEST_REDIS_DB`, all belonging
to disposable services. The runner creates a separate random database, starts
the real application and Vite, supplies the environment below, and tears down
its database/processes/data/certificates and restores `/etc/hosts` afterward.
Root is needed only inside this one-shot container for local port 80/443
sentinels and hosts entries. The outer launcher removes its service containers
and writable snapshot after the attempt.

To run the browser suite against those already-running isolated processes,
`pnpm test:e2e` consumes:

- `SUB2API_E2E_BASE_URL`: running Vue application with its real backend.
- `SUB2API_E2E_ADMIN_EMAIL` and `SUB2API_E2E_ADMIN_PASSWORD`: disposable admin
  credentials accepted by the real login endpoint.
- `SUB2API_E2E_FIXTURE_URL`: isolated network fixture control origin.
- `SUB2API_E2E_OUTPUT_DIR`: optional disposable report directory.

Missing required configuration fails the run. Tests run sequentially with no
automatic retries. Typecheck these files with
`pnpm exec tsc --noEmit --project e2e/tsconfig.json` in that same container.
The validation runtime must install Chromium using the precise Playwright
version pinned in `package.json` and remove temporary browser/report resources
afterward. Do not run validation or install browser dependencies on the host.

The independent network fixture exposes plain JSON under `/control`:

| Endpoint | Contract |
| --- | --- |
| `GET /info` | `{host, ports: {healthy, refused, held, repaired}, username, password}` |
| `POST /reset` | Clear observations and reset the held route before each case. |
| `GET /state` | `{connections: {healthy, refused, held, repaired}, held_started, credentials_leaked, direct_connections}` |
| `POST /release` | Release accepted held proxy requests; idempotent during cleanup. |
| `GET /accounts/:id` | Read the real PostgreSQL account row as `{id, name, platform, type, proxy_id, credentials}`. |

Healthy and repaired proxy probes return country `NL`; the released old probe
returns `STALE`. `held_started` acknowledges that the actual production client
has entered the held proxy, avoiding timer-based race tests. Network counters
and leaked-credential observations come from actual transport activity. Direct
TCP counters cover geo probe destinations, including incomplete requests;
production background provider probes use a separate local responder. The
fixture must not synthesize application account or proxy state.

The 14 management cases cover each platform with API Key and OAuth accounts:
proxy creation, binding persistence, deletion prevention in both UI and HTTP
service, idle route changes, real probe failure, in-flight route replacement,
old-success isolation in UI and the enriched backend proxy listing, successful repair,
explicit unbinding, deletion, and binding a replacement without changing the
account identity or credential. Account creation through the real admin API is
fixture setup; OAuth authorization itself requires its own scenario.

Traces, screenshots, and videos are disabled because these forms contain
disposable credentials. The outer validation runner owns teardown of the
application, network fixture, PostgreSQL, Redis, and temporary resources.
